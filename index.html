1. Why we cut documents into chunks

5 minutes: read

An LLM has a limited context window, and every token you send costs money and attention. A 200-page handbook cannot go into every prompt. So a RAG (Retrieval-Augmented Generation) system works in two stages:

  • Index time: split documents into chunks, turn each chunk into an embedding (a vector), and store it.
  • Query time: embed the question, find the most similar chunks, and send only those to the LLM.

The retriever can only return whole chunks. If the answer to a question was cut in half by your splitter, no later step can fix that. Chunking quality sets the ceiling for the whole pipeline.

The trade-off you will explore:

  • Too small: chunks lose context, and facts get split apart.
  • Too large: one embedding must represent many topics, so it matches nothing well, and you pay for irrelevant text.
  • Overlap: repeating a little text at each boundary protects facts that sit on the edge, at the price of more chunks.

Three strategies you will test: Fixed-size (cut every N characters), Sentence-based (never cut mid-sentence, group sentences up to N), and Recursive (try paragraphs first, then sentences, then words, so the document's own structure is respected).

4. Build it

6 minutes: read and run

The core idea in plain Python, with no libraries. Copy it into a notebook and compare with the playground:

def chunk_fixed(text, size=200, overlap=20):
    step = size - overlap            # how far the window moves
    return [text[i:i + size] for i in range(0, len(text), step)]

import re
def chunk_sentences(text, size=200):
    sents = re.split(r"(?<=[.!?])\s+", text)
    chunks, cur = [], ""
    for s in sents:
        if cur and len(cur) + len(s) + 1 > size:
            chunks.append(cur); cur = s
        else:
            cur = f"{cur} {s}".strip()
    if cur: chunks.append(cur)
    return chunks

In production, use a tested splitter (pip install langchain-text-splitters):

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,        # characters (or tokens, via length_function)
    chunk_overlap=100,
    separators=["\n\n", "\n", ". ", " ", ""],
)
chunks = splitter.split_text(document_text)

6. Using this in real AI applications

4 minutes: read
  • Start with a baseline, such as recursive splitting at roughly 300 to 800 tokens with 10 to 15% overlap. Then tune it using an evaluation set of real questions, like the one you just used. Measure; do not guess.
  • Match the splitter to the document. Markdown and code can be split by headings or functions, tables should stay whole, and PDFs need cleaning (headers, footers, hyphenation) before chunking.
  • Store metadata with each chunk (source, page, section title) so answers can cite sources and you can filter at query time.
  • Try advanced options when basics plateau: semantic chunking (split where embedding similarity drops), parent-child retrieval (search small chunks, return the larger parent), and adding a document title to every chunk.
  • Failure to watch for: an answer that is "in the documents" but never retrieved. Check chunking before blaming the LLM.
